【目标 · 持久,必须完成,不许提前收尾】
修好 dsh web;拉起会话 <SESSION-ID>;把情况告诉它。

上面两处尖括号占位符(<SESSION-ID> 和 <STATE-DIR>)不是给人手改的:install.ps1 在安装时
会把它们替换成真实的会话 id 和状态目录,再把这份提示词写进状态目录。你读到的应当是替换后的版本。

这个目标是【挂着的】:如果你觉得自己"做完了想收尾",先逐条核对下面的验收条件 ——
没全部满足就继续做,不要因为一条命令返回了就结束。
全部满足后,输出单独一行 DONE 然后退出。

背景:这个模型容易莫名其妙提前结束 response,所以目标必须一直挂着。
外部每 20 秒会重新检查一次,最多再叫我三次 —— 但你一次做完,比被反复叫更好。

【一】修好并启动 dsh web。判据是行为,不是输出:
  进程存在:命令行含 `lib\bin.js web`,并且【不含】`runner.js`、也不含 `subprocess-local`
  【并且】3080 端口处于 Listen
  "返回了命令提示符"或"打印了 node 版本号"都算失败,不算成功。
  (这两个字符串只是症状;端口被占住才是那件事本身。)
  验收:自己跑一次判据,把输出贴出来。

【二】拉起那一个会话。它的 id 是
      <SESSION-ID>
  必须按这个 id 拉,【不要】用"时间排序最近" —— 时间序会选错会话。

  通道是【被动信标】,已验证:往
      <STATE-DIR>\lid.state
  写一行,格式:
      <OPEN|CLOSED> yyyy-MM-dd HH:mm:ss <标记>
  例:OPEN 2026-09-29 15:10:00 see-SITUATION.md
  插件每 2 秒读这个文件,发现【整行】变化就给订阅者投消息;目标会话已订阅,
  订阅在 lid.subscribers.json 里持久化(重启后仍生效)。
  注意:不要写假的 OPEN/CLOSED —— 保持原来的状态词不变,只刷新时间戳和标记。

  【先查重,别重复拉】外面有两个东西在做同一件事:
    · 计划任务 `DSH-guard`(每分钟一次)
    · SYSTEM 身份的 `guard-loop.ps1`(每 20 秒一次)
  它们会把当前 dsh web 的 pid 写进 guard-last-web-pid.txt。
  如果你看到那里的 pid **已经是**你刚启动起来的那个,说明它已经拉过我了 ——
  那就【不要再写 lid.state】,只做第三步。
  验收:报告 lid.state 最终那一行,以及 guard-last-web-pid.txt 的内容。

【三】告诉他发生了什么。把情况写进
      <STATE-DIR>\SITUATION.md
  因为信标那条通知的文字由插件固定,带不了正文 —— 所以把指针写进 lid.state 那行的标记里
  (例如 see-SITUATION.md),他醒过来第一眼就知道去哪读。
  如实写:你修了什么、改了哪个文件、还有什么没修好、你不确定什么。

【不要做】
- 不要 kill 任何 node 进程,除了确实卡死的 dsh web 自己
- 不要编辑 profiles 下的模块文件(那些要重启才生效,而且能把 dsh 弄得起不来)
- 不要打印任何 key / token / 密码
- 不要把"我已经通知他了"当成回执 —— 除非你确认那条消息真的落进了他的会话
